Tipos DDD

¿Qué significa cada tipo?

Dos de los cuatro tipos DDD aparecen en esta capacidad: el catálogo que tipifica y el evento que registra el hecho.

Catálogo

Lista de referencia casi estática que tipifica otras entidades.

En seguridad: tipo_incidente — CASIPERDIDA, LESION, CAIDA_ROCA, DERRAME, ELECTRICO, INCENDIO, VEHICULO.

Evento inmutable

Hecho que ya ocurrió. Append-only: fuente de trazabilidad, también por privilegios (sin UPDATE/DELETE).

En seguridad: incidente — un hecho de seguridad capturado en el turno.

Raíz de Agregado

Entidad principal que protege reglas de consistencia.

No aplica aquí: el incidente cuelga de mina/obra (catálogos), no introduce una raíz propia.

Entidad

Objeto con identidad propia que persiste aunque cambien sus atributos.

Referenciadas: mina, obra, empleado (de catalogos).

Código SQL

DDL (PostgreSQL)

Esquema real con id UUID, multi-tenant, evento append-only e índices de búsqueda. Las FK aparecen en su forma final compuesta (id_empresa, id). Pasa el cursor sobre columnas para ver su explicación.

seguridad / tipo_incidente.sql (Catálogo por empresa) 
CREATE TABLE seguridad.tipo_incidente (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  id_empresa UUID NOT NULL,
  codigo TEXT NOT NULL,
  descripcion TEXT NOT NULL,
  requiere_paro BOOLEAN NOT NULL DEFAULT false,
  estado TEXT NOT NULL DEFAULT 'ACTIVO',
  creado_en TIMESTAMPTZ NOT NULL DEFAULT now(), creado_por_usuario_id UUID,
  actualizado_en TIMESTAMPTZ NOT NULL DEFAULT now(), actualizado_por_usuario_id UUID,
  eliminado_en TIMESTAMPTZ, eliminado_por_usuario_id UUID,
  CONSTRAINT ck_tipo_incidente_estado CHECK (estado IN ('ACTIVO','INACTIVO')),
  CONSTRAINT uq_tipo_incidente_tenant UNIQUE (id_empresa, id),
  CONSTRAINT fk_tipo_incidente_empresa FOREIGN KEY (id_empresa) REFERENCES gobierno.empresa(id) ON DELETE RESTRICT
);
CREATE UNIQUE INDEX uq_tipo_incidente ON seguridad.tipo_incidente (id_empresa, codigo) WHERE eliminado_en IS NULL;
seguridad / incidente.sql (Evento append-only) 
CREATE TABLE seguridad.incidente (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  id_empresa UUID NOT NULL,
  id_mina UUID NOT NULL,
  id_obra UUID,
  id_tipo_incidente UUID NOT NULL,
  id_reportado_por UUID,
  fecha DATE NOT NULL,
  turno TEXT NOT NULL,
  severidad TEXT NOT NULL,
  descripcion TEXT NOT NULL,
  accion_inmediata TEXT,
  creado_en TIMESTAMPTZ NOT NULL DEFAULT now(), creado_por_usuario_id UUID,
  CONSTRAINT ck_incidente_turno CHECK (turno IN ('M','V','N')),
  CONSTRAINT ck_incidente_severidad CHECK (severidad IN ('BAJA','MEDIA','ALTA','CRITICA')),
  CONSTRAINT fk_incidente_empresa FOREIGN KEY (id_empresa) REFERENCES gobierno.empresa(id) ON DELETE RESTRICT,
  CONSTRAINT fk_incidente_mina FOREIGN KEY (id_empresa, id_mina) REFERENCES catalogos.mina (id_empresa, id) ON DELETE RESTRICT,
  CONSTRAINT fk_incidente_obra FOREIGN KEY (id_empresa, id_obra) REFERENCES catalogos.obra (id_empresa, id) ON DELETE RESTRICT,
  CONSTRAINT fk_incidente_tipo FOREIGN KEY (id_empresa, id_tipo_incidente) REFERENCES seguridad.tipo_incidente (id_empresa, id) ON DELETE RESTRICT,
  CONSTRAINT fk_incidente_reportado_por FOREIGN KEY (id_empresa, id_reportado_por) REFERENCES catalogos.empleado (id_empresa, id) ON DELETE RESTRICT
);
CREATE INDEX ix_incidente_mina_fecha ON seguridad.incidente (id_empresa, id_mina, fecha);
CREATE INDEX ix_incidente_severidad ON seguridad.incidente (id_empresa, severidad, fecha);

Nota: incidente no tiene actualizado_en ni eliminado_en: es un evento puro. El rol aplicacion solo puede SELECT/INSERT (append-only por privilegio, test T40); la FK compuesta impide referenciar la mina de otra empresa (test T41).

Preguntas frecuentes

Decisiones de diseño

¿Por qué seguridad es "datos puros" y no incluye antichoque o gases?
Porque la captura de incidentes es información que un encargado registra — no necesita hardware. La detección de colisiones, fatiga, gases o el control de quién está bajo tierra (tag-in/out) son sistemas de hardware (radares, cámaras, sensores, unidades a bordo) que pertenecen a otra categoría de producto. Esta capa cubre lo valioso y barato: el registro y el análisis del incidente.
¿Por qué el incidente es append-only?
Un registro de seguridad debe preservarse tal como ocurrió: editarlo destruiría la traza. Por eso incidente solo tiene creado_en y el rol aplicacion no tiene privilegio de UPDATE ni DELETE. Una corrección se hace con un nuevo registro, dejando ambas versiones auditables — el mismo patrón que medicion en reconciliación.
¿Cómo se relaciona con las demoras de producción?
Una demora (demora_equipo) explica por qué un equipo no produjo; un incidente explica un hecho de seguridad. Cruzarlos por mina, obra, fecha y turno permite ver, por ejemplo, si las caídas de roca coinciden con paros de barrenación — una lectura que ningún sensor da, solo el dato bien estructurado.
