El territorio

Capacidades y entidades

La reconciliación cierra el ciclo: cada segmento de 10×2 m recibe una medición por cada fase (Reserva, Tumbe, Estimación, Planta), lo que permite comparar toneladas y leyes a lo largo de toda la cadena.

El segmento es la unidad mínima de trazabilidad: 10 m de largo × 2 m de ancho dentro de un rebaje. La medicion es append-only con restricción UNIQUE (id_empresa, id_segmento, fuente): garantiza que exista exactamente una fila por fase de la cadena.

Matriz de responsabilidades

¿Qué rol cumple cada tabla?

Raíz Evento Pasa el cursor para ver responsabilidad y porqué.
Raízreconciliacion

segmento

entidad nueva

Responsabilidad

Unidad física de trazabilidad: 10 m de largo × 2 m de ancho dentro de un rebaje. Cada segmento tiene un codigo único por empresa que lo identifica en toda la cadena productiva.

Por qué

Sin el segmento como entidad no hay ancla estable para comparar Reserva vs Tumbe vs Estimación vs Planta. El codigo es el hilo conductor: UNIQUE (id_empresa, codigo) WHERE eliminado_en IS NULL.

Eventoreconciliacion

medicion

evento nuevo

Responsabilidad

Registra toneladas y leyes (Au, Ag, Pb, Zn) de un segmento para una fuente específica: RESERVA, TUMBE, ESTIMACION o PLANTA. Una fila por fuente, nunca se edita.

Por qué

Evento append-only con restricción UNIQUE (id_empresa, id_segmento, fuente). Garantiza que la comparación siempre sea entre exactamente una lectura por fase, sin riesgo de duplicados o sobreescrituras.

Código SQL

DDL real (PostgreSQL)

Esquema real con id UUID, multi-tenant, auditoría inline, evento append-only e índices únicos parciales. Pasa el cursor sobre columnas resaltadas para ver su explicación.

reconciliacion / segmento.sql (Raíz de Agregado) 
CREATE TABLE reconciliacion.segmento (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  id_empresa UUID NOT NULL,
  id_mina UUID NOT NULL,
  id_rebaje UUID,
  codigo TEXT NOT NULL,
  largo_m NUMERIC(6,2) NOT NULL DEFAULT 10.0,
  ancho_m NUMERIC(6,2) NOT NULL DEFAULT 2.0,
  descripcion TEXT,
  estado TEXT NOT NULL DEFAULT 'ACTIVO',
  creado_en TIMESTAMPTZ NOT NULL DEFAULT now(), creado_por_usuario_id UUID,
  actualizado_en TIMESTAMPTZ NOT NULL DEFAULT now(), actualizado_por_usuario_id UUID,
  eliminado_en TIMESTAMPTZ, eliminado_por_usuario_id UUID,
  CONSTRAINT ck_segmento_estado CHECK (estado IN ('ACTIVO','INACTIVO')),
  CONSTRAINT fk_segmento_empresa FOREIGN KEY (id_empresa) REFERENCES gobierno.empresa(id) ON DELETE RESTRICT,
  CONSTRAINT fk_segmento_mina FOREIGN KEY (id_mina) REFERENCES catalogos.mina(id) ON DELETE RESTRICT,
  CONSTRAINT fk_segmento_rebaje FOREIGN KEY (id_rebaje) REFERENCES planeacion.rebaje(id) ON DELETE RESTRICT
);
CREATE INDEX ix_segmento_mina ON reconciliacion.segmento (id_empresa, id_mina);
CREATE UNIQUE INDEX uq_segmento ON reconciliacion.segmento (id_empresa, codigo) WHERE eliminado_en IS NULL;
reconciliacion / medicion.sql (Evento append-only) 
CREATE TABLE reconciliacion.medicion (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  id_empresa UUID NOT NULL,
  id_segmento UUID NOT NULL,
  fuente TEXT NOT NULL,
  fecha DATE NOT NULL,
  toneladas NUMERIC(14,3),
  ley_au NUMERIC(10,4),
  ley_ag NUMERIC(10,4),
  ley_pb NUMERIC(10,4),
  ley_zn NUMERIC(10,4),
  creado_en TIMESTAMPTZ NOT NULL DEFAULT now(), creado_por_usuario_id UUID,
  CONSTRAINT ck_medicion_fuente CHECK (fuente IN ('RESERVA','TUMBE','ESTIMACION','PLANTA')),
  CONSTRAINT uq_medicion UNIQUE (id_empresa, id_segmento, fuente),
  CONSTRAINT fk_medicion_empresa FOREIGN KEY (id_empresa) REFERENCES gobierno.empresa(id) ON DELETE RESTRICT,
  CONSTRAINT fk_medicion_segmento FOREIGN KEY (id_segmento) REFERENCES reconciliacion.segmento(id) ON DELETE RESTRICT
);
CREATE INDEX ix_medicion_segmento ON reconciliacion.medicion (id_segmento);

Nota: medicion no tiene actualizado_en ni eliminado_en: es un evento puro. Si hay un error, se anula con una medición correctora de la misma fuente (requiere borrar y reinsertar vía proceso controlado).

Preguntas frecuentes

Decisiones de diseño

¿Por qué segmentos de exactamente 10×2 m?
Porque esa es la unidad de avance estándar de la operación: un frente de ataque de 2 m de ancho barrenado en una secuencia de 10 m. Discretizar en segmentos de esa dimensión permite comparar directamente lo planeado en reservas con lo tumbado y lo entregado a planta, sin conversiones ad-hoc. Los valores largo_m y ancho_m tienen DEFAULT en el DDL para ese estándar, pero son editables si la geometría real difiere.
¿Por qué medicion es append-only con una sola fila por fuente?
La restricción UNIQUE (id_empresa, id_segmento, fuente) garantiza que para cada segmento exista exactamente un dato por fase. Así la diferencia Tumbe − Reserva siempre es un cálculo determinista: no hay ambigüedad sobre qué fila usar. El append-only preserva el historial: si un valor fue capturado, queda registrado. Cualquier corrección debe pasar por un proceso controlado (borrado + nueva inserción), lo que crea una traza de auditoría explícita.
¿Cómo se calcula la diferencia Tumbe vs Reserva?
Con un JOIN entre dos filas de medicion del mismo segmento, filtrando por fuente:

SELECT s.codigo,
  m_r.toneladas AS ton_reserva, m_t.toneladas AS ton_tumbe,
  (m_t.toneladas - m_r.toneladas) AS diferencia
FROM reconciliacion.segmento s
JOIN reconciliacion.medicion m_r ON m_r.id_segmento = s.id AND m_r.fuente = 'RESERVA'
JOIN reconciliacion.medicion m_t ON m_t.id_segmento = s.id AND m_t.fuente = 'TUMBE'
WHERE s.id_empresa = $1;

La misma lógica aplica para Tumbe vs Estimación o Estimación vs Planta. Si falta alguna fila (la medición de esa fuente aún no existe), el JOIN interior excluye el segmento naturalmente; un LEFT JOIN lo muestra con NULL en la diferencia.
¿Por qué el codigo del segmento tiene índice único parcial?
Un UNIQUE … WHERE eliminado_en IS NULL garantiza unicidad solo entre segmentos activos: si un segmento se da de baja (borrado lógico) y luego se necesita reutilizar su código, es posible sin violar la restricción. Esto mantiene la integridad referencial en activos sin bloquear reasignaciones históricas.
