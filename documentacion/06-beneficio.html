El territorio

Capacidad y entidades

La capacidad beneficio recibe el mineral acarreado desde mina, lo procesa en la planta de molienda y registra el balance metalúrgico lote a lote. Cada lote captura las leyes en los tres puntos del proceso (cabeza, concentrado, cola) y la recuperación porcentual por cada metal valioso.

Tipos DDD

Clasificación de las tablas

La raíz de agregado es el lote; las leyes y recuperaciones son eventos append-only que describen lo que ocurrió en el proceso metalúrgico.

Raíz de Agregado

Entidad principal y puerta de entrada al lote de molienda. Controla el estado (ABIERTO / CERRADO) y las reglas de consistencia del agregado.

Aquí: lote_molienda

Evento inmutable

Hecho que ya ocurrió en el proceso metalúrgico. No se edita ni se borra (append-only): fuente de trazabilidad del balance y base para la comparativa.

Aquí: ley_metalurgica, recuperacion

Raízbeneficio

lote_molienda

entidad nueva

Responsabilidad

Lote de mineral procesado en planta: mina, código de lote, fecha, toneladas molidas y estado (ABIERTO / CERRADO). Es la puerta de entrada al agregado metalúrgico.

Por qué

Ancla todos los registros de ley y recuperación. El estado CERRADO congela el lote impidiendo nuevas mediciones; el ABIERTO permite actualizarlo a lo largo del turno o día.

Eventobeneficio

ley_metalurgica

evento nuevo

Responsabilidad

Ley (g/t o %) de cada metal por punto del proceso: CABEZA (entrada a planta), CONCENTRADO (salida valiosa) y COLA (desecho). Registra ley_au, ley_ag, ley_pb y ley_zn en un mismo registro.

Por qué

Evento append-only porque la ley medida es un hecho histórico. El UNIQUE por (id_empresa, id_lote_molienda, punto) garantiza exactamente un registro por punto por lote; la comparativa CABEZA vs COLA cuantifica la eficiencia metalúrgica.

Eventobeneficio

recuperacion

evento nuevo

Responsabilidad

Recuperación metalúrgica porcentual por metal (AU, AG, PB, ZN): cuánto del metal en cabeza logró pasar al concentrado. Rango 0–100 % por constraint.

Por qué

Evento separado de ley_metalurgica porque la recuperación es un indicador derivado del proceso, medido o calculado de forma independiente. El UNIQUE por (id_empresa, id_lote_molienda, metal) garantiza un valor por metal por lote.

DDL reconciliado (PostgreSQL)

Esquema real con id UUID, multi-tenant, auditoría inline y eventos append-only. Pasa el cursor sobre las columnas resaltadas para ver su explicación.

beneficio / lote_molienda.sql (Raíz de Agregado) 
CREATE TABLE beneficio.lote_molienda (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  id_empresa UUID NOT NULL,
  id_mina UUID NOT NULL,
  codigo_lote TEXT NOT NULL,
  fecha DATE NOT NULL,
  toneladas_molidas NUMERIC(14,3) NOT NULL DEFAULT 0,
  estado TEXT NOT NULL DEFAULT 'ABIERTO',
  creado_en TIMESTAMPTZ NOT NULL DEFAULT now(), creado_por_usuario_id UUID,
  actualizado_en TIMESTAMPTZ NOT NULL DEFAULT now(), actualizado_por_usuario_id UUID,
  eliminado_en TIMESTAMPTZ, eliminado_por_usuario_id UUID,
  CONSTRAINT ck_lote_estado CHECK (estado IN ('ABIERTO','CERRADO')),
  CONSTRAINT fk_lote_empresa FOREIGN KEY (id_empresa) REFERENCES gobierno.empresa(id) ON DELETE RESTRICT,
  CONSTRAINT fk_lote_mina FOREIGN KEY (id_mina) REFERENCES catalogos.mina(id) ON DELETE RESTRICT
);
CREATE INDEX ix_lote_mina_fecha ON beneficio.lote_molienda (id_empresa, id_mina, fecha);
CREATE UNIQUE INDEX uq_lote_molienda ON beneficio.lote_molienda (id_empresa, id_mina, codigo_lote) WHERE eliminado_en IS NULL;
beneficio / ley_metalurgica.sql (Evento append-only — ley por punto del proceso) 
CREATE TABLE beneficio.ley_metalurgica (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  id_empresa UUID NOT NULL,
  id_lote_molienda UUID NOT NULL,
  punto TEXT NOT NULL,
  ley_au NUMERIC(10,4),
  ley_ag NUMERIC(10,4),
  ley_pb NUMERIC(10,4),
  ley_zn NUMERIC(10,4),
  creado_en TIMESTAMPTZ NOT NULL DEFAULT now(), creado_por_usuario_id UUID,
  CONSTRAINT ck_ley_punto CHECK (punto IN ('CABEZA','CONCENTRADO','COLA')),
  CONSTRAINT uq_ley_metalurgica UNIQUE (id_empresa, id_lote_molienda, punto),
  CONSTRAINT fk_ley_empresa FOREIGN KEY (id_empresa) REFERENCES gobierno.empresa(id) ON DELETE RESTRICT,
  CONSTRAINT fk_ley_lote FOREIGN KEY (id_lote_molienda) REFERENCES beneficio.lote_molienda(id) ON DELETE RESTRICT
);
CREATE INDEX ix_ley_lote ON beneficio.ley_metalurgica (id_lote_molienda);
beneficio / recuperacion.sql (Evento append-only — recuperación metalúrgica por metal) 
CREATE TABLE beneficio.recuperacion (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  id_empresa UUID NOT NULL,
  id_lote_molienda UUID NOT NULL,
  metal TEXT NOT NULL,
  recuperacion_pct NUMERIC(6,2),
  creado_en TIMESTAMPTZ NOT NULL DEFAULT now(), creado_por_usuario_id UUID,
  CONSTRAINT ck_recuperacion_metal CHECK (metal IN ('AU','AG','PB','ZN')),
  CONSTRAINT ck_recuperacion_pct CHECK (recuperacion_pct IS NULL OR (recuperacion_pct >= 0 AND recuperacion_pct <= 100)),
  CONSTRAINT uq_recuperacion UNIQUE (id_empresa, id_lote_molienda, metal),
  CONSTRAINT fk_recuperacion_empresa FOREIGN KEY (id_empresa) REFERENCES gobierno.empresa(id) ON DELETE RESTRICT,
  CONSTRAINT fk_recuperacion_lote FOREIGN KEY (id_lote_molienda) REFERENCES beneficio.lote_molienda(id) ON DELETE RESTRICT
);
CREATE INDEX ix_recuperacion_lote ON beneficio.recuperacion (id_lote_molienda);

gobierno.empresa y catalogos.mina se consumen por FK desde esta capacidad. La ley se captura una vez por punto por lote; la recuperación, una vez por metal por lote.

Preguntas frecuentes

Decisiones de diseño

¿Por qué las leyes se registran por punto del proceso y no solo la de cabeza?
Porque el balance metalúrgico necesita los tres: la cabeza es lo que entra a planta (debe coincidir con la ley declarada en mina), el concentrado es el producto que se vende o envía a fundición, y la cola es lo que se descarta. Sin las tres no es posible calcular el factor de enriquecimiento ni auditar pérdidas en el proceso. El constraint CHECK (punto IN ('CABEZA','CONCENTRADO','COLA')) cierra el catálogo de valores válidos.
¿Por qué ley_metalurgica y recuperacion son eventos append-only?
Porque una vez que la planta midió y registró la ley o el porcentaje de recuperación, ese hecho ya ocurrió. Si el valor fuera incorrecto, el proceso correcto es registrar una entrada nueva (corrección explícita con trazabilidad), no sobreescribir el anterior. Esto también simplifica el sync: los eventos solo necesitan llegar al central, nunca se actualizan de vuelta al dispositivo.
¿Cómo alimenta esta capacidad la comparativa producción vs molienda?
La producción registra las toneladas acarreadas por obra y turno (acarreo_viaje.toneladas). La planta registra las toneladas que realmente ingresaron a molienda (lote_molienda.toneladas_molidas) y la ley en cabeza (ley_metalurgica con punto = 'CABEZA'). La comparativa cruza ambas fuentes por mina y período: si las toneladas o leyes difieren, hay una merma, un error de muestreo o una dilución no contabilizada.
¿Por qué la recuperación está en tabla separada y no como columnas en ley_metalurgica?
Porque la recuperación es un cálculo o medición independiente a las leyes: puede llegar en un momento distinto y puede existir solo para algunos metales. Separar en una tabla con discriminador metal permite registrar la recuperación de Au tan pronto se conoce, sin esperar las demás. El UNIQUE (id_empresa, id_lote_molienda, metal) garantiza un registro por metal por lote.
