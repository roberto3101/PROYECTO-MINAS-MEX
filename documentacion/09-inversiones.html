Matriz de responsabilidades

¿Qué rol cumple cada tabla?

Raízinversiones

activo

activo capitalizable

Responsabilidad

Bien capitalizable de la mina: código, descripción, tipo de activo, costo de adquisición, fecha y vida útil en meses. Porta el ciclo de vida ACTIVO / BAJA.

Por qué

Es la raíz del agregado porque concentra la identidad y las reglas del bien. El UUID garantiza unicidad por empresa (índice único parcial sobre codigo donde no esté de baja).

Entidadinversiones

inversion

inversión por obra y periodo

Responsabilidad

Registro del capital invertido en una obra durante un periodo mensual (YYYY-MM): concepto, monto y moneda (USD / MXN). La obra es opcional para permitir inversiones generales de mina.

Por qué

Entidad mutable (puede corregirse el monto o concepto) vinculada tanto a la mina como a la obra, lo que habilita resúmenes por labor o por periodo sin duplicar datos.

Evento inmutableinversiones

consumo_acero

acero consumido — append-only

Responsabilidad

Cada registro de acero (barra helicoidal, malla, split set, etc.) consumido en una obra y fecha: tipo, cantidad y unidad. Solo tiene columnas de creación; nunca se actualiza.

Por qué

Evento append-only: es un hecho consumado. La inmutabilidad garantiza trazabilidad del insumo más costoso del sostenimiento y facilita el sync offline (solo INSERT, nunca UPDATE/DELETE).

Código SQL

DDL real (PostgreSQL)

Esquema real con id UUID, multi-tenant, auditoría inline y evento append-only. Pasa el cursor sobre las columnas destacadas para ver su explicación.

inversiones / activo.sql (Raíz de Agregado) 
CREATE TABLE inversiones.activo (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  id_empresa UUID NOT NULL,
  id_mina UUID NOT NULL,
  codigo TEXT NOT NULL,
  descripcion TEXT NOT NULL,
  tipo_activo TEXT,
  costo_adquisicion NUMERIC(16,2) NOT NULL DEFAULT 0,
  fecha_adquisicion DATE,
  vida_util_meses INTEGER,
  estado TEXT NOT NULL DEFAULT 'ACTIVO',
  creado_en TIMESTAMPTZ NOT NULL DEFAULT now(), creado_por_usuario_id UUID,
  actualizado_en TIMESTAMPTZ NOT NULL DEFAULT now(), actualizado_por_usuario_id UUID,
  eliminado_en TIMESTAMPTZ, eliminado_por_usuario_id UUID,
  CONSTRAINT ck_activo_estado CHECK (estado IN ('ACTIVO','BAJA')),
  CONSTRAINT fk_activo_empresa FOREIGN KEY (id_empresa) REFERENCES gobierno.empresa(id) ON DELETE RESTRICT,
  CONSTRAINT fk_activo_mina FOREIGN KEY (id_mina) REFERENCES catalogos.mina(id) ON DELETE RESTRICT
);
CREATE UNIQUE INDEX uq_activo ON inversiones.activo (id_empresa, codigo) WHERE eliminado_en IS NULL;
inversiones / inversion.sql (Entidad — inversión por obra y periodo) 
CREATE TABLE inversiones.inversion (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  id_empresa UUID NOT NULL,
  id_mina UUID NOT NULL,
  id_obra UUID,
  periodo TEXT NOT NULL,
  concepto TEXT NOT NULL,
  monto NUMERIC(16,2) NOT NULL DEFAULT 0,
  moneda TEXT NOT NULL DEFAULT 'USD',
  creado_en TIMESTAMPTZ NOT NULL DEFAULT now(), creado_por_usuario_id UUID,
  actualizado_en TIMESTAMPTZ NOT NULL DEFAULT now(), actualizado_por_usuario_id UUID,
  eliminado_en TIMESTAMPTZ, eliminado_por_usuario_id UUID,
  CONSTRAINT ck_inversion_moneda CHECK (moneda IN ('USD','MXN')),
  CONSTRAINT fk_inversion_empresa FOREIGN KEY (id_empresa) REFERENCES gobierno.empresa(id) ON DELETE RESTRICT,
  CONSTRAINT fk_inversion_mina FOREIGN KEY (id_mina) REFERENCES catalogos.mina(id) ON DELETE RESTRICT,
  CONSTRAINT fk_inversion_obra FOREIGN KEY (id_obra) REFERENCES catalogos.obra(id) ON DELETE RESTRICT
);
CREATE INDEX ix_inversion_mina_periodo ON inversiones.inversion (id_empresa, id_mina, periodo);
inversiones / consumo_acero.sql (Evento append-only) 
CREATE TABLE inversiones.consumo_acero (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  id_empresa UUID NOT NULL,
  id_mina UUID NOT NULL,
  id_obra UUID,
  fecha DATE NOT NULL,
  tipo_acero TEXT NOT NULL,
  cantidad NUMERIC(14,3) NOT NULL,
  unidad TEXT NOT NULL DEFAULT 'kg',
  creado_en TIMESTAMPTZ NOT NULL DEFAULT now(), creado_por_usuario_id UUID,
  CONSTRAINT ck_acero_cantidad CHECK (cantidad >= 0),
  CONSTRAINT fk_acero_empresa FOREIGN KEY (id_empresa) REFERENCES gobierno.empresa(id) ON DELETE RESTRICT,
  CONSTRAINT fk_acero_mina FOREIGN KEY (id_mina) REFERENCES catalogos.mina(id) ON DELETE RESTRICT,
  CONSTRAINT fk_acero_obra FOREIGN KEY (id_obra) REFERENCES catalogos.obra(id) ON DELETE RESTRICT
);
CREATE INDEX ix_acero_mina_fecha ON inversiones.consumo_acero (id_empresa, id_mina, fecha);

Preguntas frecuentes

Decisiones de diseño

¿Qué es un activo capitalizable y por qué tiene su propia tabla?
Un activo capitalizable es un bien (compresor, jumbo, subestación eléctrica, etc.) cuyo costo no se lleva directamente a gastos sino que se capitaliza y se deprecia a lo largo de su vida útil. Tener su propia tabla permite asignarle costo_adquisicion, fecha_adquisicion y vida_util_meses para calcular la depreciación, y gestionar el ciclo de vida (ACTIVO / BAJA) sin mezclar esa lógica con el registro de inversiones de obra.
¿Por qué consumo_acero es append-only (evento inmutable)?
El acero (barras helicoidales, malla electrosoldada, split sets) es el insumo de sostenimiento más costoso de la operación. Una vez colocado en la obra es un hecho consumado: no se puede desinstalar ni ajustar retroactivamente. Modelarlo como evento append-only — solo columnas creado_en, sin actualizado_en — garantiza trazabilidad completa, simplifica el sync offline (solo INSERTs) y preserva el historial real para auditorías o reclamaciones a proveedores.
¿Para qué sirve registrar la inversión por obra y no solo por mina?
Porque el control de capital más valioso no es ¿cuánto gastamos en la mina? sino ¿cuánto gastamos en la obra RPA-2400W?. Vincular cada inversion a un id_obra permite comparar el plan de inversión contra el gasto real labor por labor, identificar obras que consumen capital desproporcionado y priorizar el presupuesto del siguiente periodo. La obra es opcional (NULL) para registrar inversiones generales de infraestructura que no se pueden asignar a una labor específica.
¿Por qué el índice único de activo es parcial (WHERE eliminado_en IS NULL)?
Un índice único parcial garantiza que no existan dos activos con el mismo codigo dentro de una empresa mientras estén activos. Si un bien se da de baja (eliminado_en IS NOT NULL), queda fuera del índice y el código puede reutilizarse para un activo nuevo — por ejemplo, al reponer un equipo dado de baja. Esto evita conflictos de clave sin perder el historial de los bienes retirados.
